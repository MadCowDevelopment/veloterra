# 10.1 Authentication and Authorization

<details>
<summary>Documentation Hints</summary>

Describe identity, authentication, authorization, session handling, and protected resources. No formal security standard is claimed.
</details>

## Authentication

- Authentication is optional; signed-out use remains device-local.
- Google or Microsoft OAuth is initiated through Supabase Auth. Microsoft sign-in uses Microsoft Entra ID.
- OAuth returns to the application origin plus build-time base path.
- Supabase persists and refreshes the browser session.
- Anonymous Supabase users are treated as signed out by application state.

## Authorization

- The browser contains a Supabase publishable key, which is not a secret.
- Authorization must be enforced by PostgreSQL Row Level Security.
- Explored and wallet resources are keyed by `user_id`.
- Ride rows contain `user_id`; user policies must restrict all operations to `auth.uid()`.
- The application has no administrative role or service-role credential.
- Team membership, invitations, recommendations, shared cells, live presence, and
	audit history are separate authorization domains. Team reads require active
	membership; Captain and Officer permissions are checked in authenticated RPCs.
- Username lookup is an authenticated exact-match RPC. Team member displays use
	display name and username, not email.
- Live position is off by default and is written only through a rate-limited RPC for
	the selected team. Presence rows expire server-side and are cleared on lifecycle
	changes.

## Session Consequences

- A real authenticated user triggers synchronization at login and when the app becomes visible.
- Sign-out removes the cloud session but does not erase device-local progress.
- Local reset does not delete cloud records; a later sync can restore cloud-only data.
